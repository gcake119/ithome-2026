# 2026 iThome 鐵人賽｜30 天系列章節結構與文章網站交接

> 本文件依 30 篇最新定稿重新整理，作為 `gcake119/ithome-2026` 首頁、系列導覽、sidebar 與文章章節 metadata 的正式依據。若與早期企劃 Part 分法不同，以本文件為準。文章正文與標題仍以各 Day Markdown 為準。

## 系列名稱

**AI 都會寫程式了，我還要學什麼？——從「做得出來」到學會開發的 30 天**

整個系列追問：當 AI 讓實作能力跑在理解前面，一個仍在學習中的開發者，如何從真實產品與委託專案裡，逐漸知道自己還需要理解哪些產品問題、工程問題，以及 Coding 本身需要理解到什麼程度。

系列閱讀原則：**先有問題，後來才有語言。**

## 正式五章

### 第一章｜實作跑在理解前面

- Day 1｜做得出來，卻完全改不動
- Day 2｜當實作跑得比理解更快

短介：我曾經靠 AI 做出真的能運作的網站，卻不知道功能該去哪裡改，也看不見需求和結果之間發生了什麼。當實作能力跑在理解前面，我的學習順序也跟著改變：不是先學會所有概念才開始做，而是先遇到真實問題，再逐漸知道那些問題可以怎麼描述。

### 第二章｜第一個產品：從做功能，到開始理解工作

- Day 3～11

短介：第一個預約管理產品，是從觀察現場、提出願望，再把需求一個一個做成功能開始的。我嘗試用 LINE、既有工具和自動化接起原本分散的工作，也逐漸發現：人的經驗裡藏著許多沒有說出口的條件，系統處理事情的方式不一定適合直接變成使用者流程，而功能都能運作，也不代表產品已經完成。走到最後，我必須重新追問：自己真正要解決的，究竟是什麼問題？

主要推進：需求從觀察與許願長出來 → LINE 影響產品形式 → 借用成熟工具 → 分辨固定工作與人的判斷 → 看見隱含條件 → AI 反問暴露理解缺口 → 系統流程與使用者流程分開 → 功能完成與產品完成分開 → 重新檢查問題框架。

### 第三章｜第二個專案：理解工作的能力開始變成工程判斷

- Day 12～20

短介：面對一套完全陌生的行政工作，我先聽現場怎麼說、看他們怎麼做，再把零散操作整理成工作流程。沿著這些流程，我開始看見系統需要管理哪些狀態與條件、產品要怎麼幫人完成每天的工作，以及一項功能進入系統後應該由哪些部分負責。以前常在實作後才發現的問題，逐漸能在實作以前被提出，並進一步變成對系統責任、跨 repo 協作、決策理由與必要保證的工程判斷。

主要推進：Day 12 從第二個產品回看第一個產品留下的「翻譯」能力 → 現場觀察與流程圖 → 從工作流程看系統責任 → 今日工作台與 actionability → 從工作終點反推功能 → 拆系統責任 → multi-repo 與跨 repo 脈絡 → 決策紀錄 → 系統必須保證的條件。

公開描述合作專案時統一使用：**合作單位委託的內部行政流程進度管理工具**。不要公開真實合作單位、特定案件業務、個資、不必要的內部流程或部署資訊。

### 第四章｜AI 寫大量程式後，我怎麼理解、判斷與相信實作？

- Day 21～27

短介：當 Coding Agent 開始完成大量實作，我直接閱讀的程式碼反而變少了，但對工作流程、規格、系統責任與資料流的理解逐漸增加。這一章試著分辨「理解系統」和「理解程式碼」的差異，也整理我在無法逐行驗證實作時，如何透過規格、測試、AI review 與人工操作累積證據。這些方法能建立信任，卻不能帶來完全確定，也讓我更清楚看見自己在完整 QA 上仍然存在的能力缺口。

主要推進：透過規格/design理解系統 → 概念變成自己的判斷 → system-level 與 code-level understanding 分開 → SDD／TDD／AI review／人工 UI 驗收的多層證據 → 測試約束已知期待 → review 檢查實作方式 → 保留完整 QA 仍是能力缺口。

### 第五章｜回到最開始的問題：我現在知道自己還在學什麼

- Day 28～30

短介：回頭整理兩個產品留下的經驗，我開始知道，做產品以前要先看懂人怎麼完成工作；工作真的進入系統後，則要繼續追問系統必須保證什麼、誰負責守住這些條件，以及要靠哪些證據確認實作成立。但這些產品與工程判斷，仍不能代替對程式本身的理解。30 天最後沒有替「Coding 要懂多深」畫出共同門檻，而是讓我更具體地看見：自己已經理解了什麼，下一步還需要往哪裡學。

收束順序：Day 28 產品／需求 → Day 29 工程 → Day 30 Coding。Day 30 保留「程式實作究竟需要理解到多深」為未解問題，不宣稱 AI 時代不需要 Coding，也不設定普遍適用的最低門檻。

## 網站實作規則

1. 正式 Day 順序固定為 Day 1～30，不因章節重整而重新排序。
2. 正式網站分組只使用以上五章，不再使用舊的產品篇／工程篇／可靠性篇等分類。
3. 章節資訊屬於 metadata；不要為增加章節而修改文章正文。
4. 現行 repo 的正式文章 collection 是 `src/content/ironman/day-NN.md`，由 `src/content.config.ts` 與 `scripts/ithome/prepare.mjs` 共同使用；不要另外建立第二套 `src/content/posts/` 文章來源。
5. 對應 section id：Day 1–2=`chapter-1`；Day 3–11=`chapter-2`；Day 12–20=`chapter-3`；Day 21–27=`chapter-4`；Day 28–30=`chapter-5`。
6. 首頁、sidebar、單篇章節標示應由 `ithome.config.json` 的 `learningMap.sections` 與各文 frontmatter `section` 動態產生。
7. 固定文章網址保持 `/day/01/`～`/day/30/`。
